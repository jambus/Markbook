# Feature Specification: Android 客户端实现加固

**Status**: In Progress  
**Priority**: P0  
**Depends on**: 001-local-markdown-notebook, 002-camera-attachments, 004-harmony-4-5-compatibility, 005-harmonyos4-android-apk, 007-design-knowledge-base

## Goal

修复 HarmonyOS 4 Android APK 现有实现中会造成用户内容被改写、保存不生效、界面卡顿与资源泄漏的缺陷，使 Vault 契约与设计原则在真实设备上真正成立。

本规格不新增用户功能，只针对既有实现的正确性、稳定性与性能。

## User Stories

### US1 用 Markbook 打开笔记不会破坏 Obsidian 里写好的内容（P0）

用户在 Obsidian 中写有代码块、表格、有序列表、嵌套列表、引用和 YAML front matter 的笔记，用 Markbook 打开、编辑其中一段并保存后，未触及的部分与原文逐字节一致。

**Acceptance**: 含上述结构的样例笔记经「打开 → 编辑首段 → 保存」后，除被编辑段落外的原始文本与缩进保持不变。

### US2 保存状态可信（P0）

用户输入后无需手动操作，正文会在短暂停顿后自动落盘，状态提示与实际写入结果一致。

**Acceptance**: 输入停止约 0.6 秒后状态由「未保存」变为「已保存」，且文件内容确已更新；未编辑的笔记不会被写入。

### US3 大 Vault 仍可流畅浏览（P1）

用户的 Vault 含数百篇笔记时，进入目录、滚动列表和返回上一级不出现明显卡顿或无响应。

**Acceptance**: 单个目录含 200 篇笔记时，进入该目录不触发 ANR，列表滚动不掉帧到不可用程度。

### US4 反复进出编辑器不劣化（P1）

用户在浏览器与编辑器之间往返多次后，应用内存占用保持稳定，不出现闪退。

**Acceptance**: 连续进出编辑器 20 次，不产生持续增长的 WebView 实例。

### US5 中断后可恢复（P1）

拍照写入或笔记保存过程中应用被系统回收，重启后笔记与附件仍处于可解释的一致状态。

**Acceptance**: 任意目录下的中断保存都能在下次启动时被恢复，不仅限于每日笔记目录。

## Functional Requirements

### 内容保真

- **FR-801** Markdown 往返必须无损：应用不得因渲染或序列化改变用户未编辑的正文，包括缩进、空行数量、块级结构与 `<`、`&` 等字符的原始写法。
- **FR-802** 编辑器无法保真编辑的块级结构（围栏代码块、缩进代码块、表格、有序列表、嵌套列表、引用块、水平线、任务列表、YAML front matter）必须以原文逐字保留并回写。
- **FR-803** 链接必须以原始 Markdown 目标回写，不得被规范化为绝对 URL；相对路径语义以 `004` 的 Vault 契约为准。
- **FR-804** 未发生用户编辑的笔记不得被写入。

### 保存与恢复

- **FR-805** 自动保存必须在输入停止后按约定延迟真实触发，状态提示必须反映实际写入结果。
- **FR-806** 保存事务的崩溃恢复必须覆盖用户可编辑的全部目录，而不仅是每日笔记目录。
- **FR-807** 保存流程不得因回调未触发而进入永久阻塞状态；并发保存请求的完成回调不得被丢弃。
- **FR-808** 应用必须在进程重建后恢复当前所处界面、当前笔记与浏览路径。

### 性能与资源

- **FR-809** Vault 的目录枚举、正文读取与写入不得阻塞主线程。
- **FR-810** 列表项摘要必须基于有界读取，不得为生成预览而读取整篇笔记。
- **FR-811** 长列表必须使用可回收的列表容器，避免为每个条目常驻视图。
- **FR-812** 编辑器销毁时必须释放 WebView 实例。
- **FR-813** 照片预览解码必须限制在设备显示所需的尺寸内，避免超大位图导致内存不足。
- **FR-814** 后台任务的界面回调必须在宿主已销毁时安全终止。

### 平台与工程

- **FR-815** 相机输出 URI 必须通过平台提供的 FileProvider 接口生成并授权。
- **FR-816** 编辑器必须阻止富文本粘贴引入任意 HTML，仅接受纯文本。
- **FR-817** 正文字号必须响应系统字体缩放设置。
- **FR-818** Markdown 编解码逻辑必须可在不依赖 Android 框架的前提下被单元测试覆盖。

## 需求追溯

本规格是加固类规格，不产生新的产品约束。每条需求都还原一条已存在的约束：

| 需求 | 还原的原始约束 |
| --- | --- |
| FR-801、FR-802、FR-803 | `004` 的 [共享 Vault 契约](../004-harmony-4-5-compatibility/contracts/vault-contract.md)：Markdown 与相对链接必须可被 Obsidian 等工具原样理解 |
| FR-804 | [设计原则](../../design/design_principles.md) 第 1 条「文件优先，所有权归用户」：不得静默改写用户内容 |
| FR-805、FR-807 | [设计原则](../../design/design_principles.md) 第 2 条「记录应当即时，保存应当可信」与第 6 条「让状态可见」 |
| FR-806 | `004` 的保存事务与恢复语义 |
| FR-808 | [设计原则](../../design/design_principles.md) 第 8 条「导航保留方向与上下文」 |
| FR-809、FR-810、FR-811 | [设计原则](../../design/design_principles.md) 第 2 条：现场记录必须足够快速 |
| FR-812、FR-813、FR-814 | `002` 的[拍照附件规格](../002-camera-attachments/spec.md)与[拍照流程](../../design/capture_flow.md)：失败不得改写已保存正文 |
| FR-815 | `002` 的拍照落盘要求 |
| FR-816 | `001` 的[本地笔记规格](../001-local-markdown-notebook/spec.md)：正文必须保持为可迁移的 Markdown |
| FR-817 | [设计原则](../../design/design_principles.md) 第 7 条「默认可读、可触达」 |
| FR-818 | 仓库测试约定：Android 逻辑使用 JUnit 覆盖 |

同类缺陷若也存在于 HarmonyOS 5/6 HAP，由 `006` 另立任务，不在本规格内声明已修复。

## Out of Scope

- 新增笔记的新建、重命名、删除与搜索能力。
- 目标 SDK 升级、Material Components 迁移与视觉重构（另立规格）。
- HarmonyOS 5/6 HAP 端的对应实现（由 `006` 承担）。
- 远程同步相关行为（由 `003` 承担）。
